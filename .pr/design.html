One durable board for a conversation tree

Agents can read who owns work, claim it atomically, and record completion without asking another agent or keeping a browser connected. The root conversation owns the state and its deletion removes the board.

Before

TaskTracker plans belong to one conversation. There is no shared server board or atomic ownership operation. Canvas's proposed branch snapshot depends on a connected client.

After

Authenticated REST operations and an opt-in agent tool resolve the existing parent links. Members share a persisted board with versioned writes, dependency validation and one winner for a competing claim.

Request ownership and persistence

Conversation-bound tool / typed clientAuthenticated REST Read parent links under file lockValidate + compare revisionfsync + atomic replace

task_board.py: TaskBoardStore reads only identity and parent metadata. It does not hydrate an agent, require a runtime lease, contact a model, or attach a WebSocket. All blocking file operations execute off the event loop.

The authoritative board lives at <conversations>/<root hex>/task_board.json. .task-board.lock lives outside conversation directories, so deleting a root cannot replace a lock while another process waits. The first implementation serializes all board operations with one lock; this favors a small, auditable transaction boundary over a new database or registry.

The claim transaction

Both members read task version 0, owner=null, status=todo.
Member A holds the lock: version matches; dependencies are done.
  → persist owner=A, status=in_progress, version=1; release lock.
Member B acquires the lock and re-reads version 1.
  → 409 {detail: "Task version is stale", current_task: {owner: A, version: 1, …}}.
Repeating A's claim also fails; it does not create another claim.

Lifecycle and validation

  • Statuses: todo / in_progress / done, reusing TaskTracker normalization, plus blocked. The tracker is unchanged and doing remains invalid.
  • Owner and blocking by are conversation UUIDs in the same tree. A role alone is rejected.
  • Unknown and cyclic dependencies are rejected. Unfinished dependencies prevent claims.
  • Blocked requires reason + by; other states clear that payload. Done requires a completion commit.
  • Updates use CAS too. Ownership transfer requires release to todo, then a new claim.
  • Root removal uses the transaction lock; late member requests fail 404. Removing another member retains the board.
  • Rejected input values are omitted from validation errors. Board models forbid extra fields. No credential fields or PR references are introduced.

Compatibility and boundaries

Existing conversation, settings, event, TaskTracker and REST contracts remain unchanged. The tool is opt-in. REST operations are exported in OpenAPI; TypeScript exposes TaskBoardClient and AgentServerClient.taskBoards. The existing generated TypeScript contract remains tied to its published release pin.

The session key retains server-wide authority. Member ids are a tree-scope boundary, not new agent authentication; trusted hosts supply them and the tool binds its own id.

Outer Docker/hybrid REST calls stay on the catalog. Isolated runtime containers mount only their own conversation directory. Their agent tools require a separate narrowly scoped bridge to access an outer multi-runtime tree. This proposal preserves that isolation and does not forward outer credentials into containers.

No mailbox, queue, scheduler, Canvas renderer, branch snapshot, git action or PR action is added.

Review evidence

Focused tests cover HTTP and cross-process competing claims, duplicate claims, dependencies, blocked/completed transitions, scope/auth rejection, invalid and corrupt state, failed writes, deletion races, persistence, and root ownership. A real HTTP test kills and restarts the server with the same storage and exercises the actual agent tool. See the PR validation notes for executed results and environment limits.
